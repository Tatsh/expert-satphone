# Build-time patches

This reconstruction aims to be faithful to the shipped binary. One preprocessor flag gates the
deliberate deviations needed to build a playable game on current iOS, so a faithful build (with the
flag undefined) stays as close to the original as possible.

- **`ENABLE_PATCHES`** — modern-iOS compatibility fixes and fallbacks for online services that no
  longer exist. It is declared at `CMakeLists.txt:78`, defaults to `OFF`, and is defined for every
  translation unit by `CMakeLists.txt:225`. Enable it with `-DENABLE_PATCHES=ON` in any build
  configuration.

Each patch site is written as `#ifdef ENABLE_PATCHES` where the patch adds behaviour, or
`#ifndef ENABLE_PATCHES` where it removes faithful behaviour, with the original kept under `#else`
wherever both make sense. Every site carries a comment beginning "Preservation patch, not in the
binary" and the `@ghidraAddress` evidence for what the original did.

One change is not compiled at all: `Info.plist` is generated by `configure_file`, so its patched
key is chosen at configure time rather than compile time. It is listed under
[Bundle metadata](#bundle-metadata). Changing the flag therefore requires re-running CMake, not
just rebuilding.

Patches are labelled by why they exist:

- **Modern iOS** — an API or UIKit behaviour changed under code that was correct when it shipped.
- **Dead service** — a Konami server that no longer answers, leaving a flow unable to complete.

## `ENABLE_PATCHES`

### Tutorial overlays

**File:** `Project/JubeatAppDelegate.m` — `+initialize` (0x7b60)

Both tutorial overlays are one-shot: the search overlay in `-[MusicSelectViewController loadView]`
(0x22e78) and the extend-chart overlay in `-musicViewTapped:` (0x2af98) each run only while their
key reads false, and each writes its key back as it appears. The bundled `DefaultSettings.plist`
ships `PrefSearchTutorialFinish` and `PrefExtendTutorialFinish` already true, which is what stops
either from ever being shown.

The patch registers both keys as true alongside the plist. That decouples the patched build from the
resource, so the two keys can be dropped from `DefaultSettings.plist` to let an unpatched build run
the tutorials without the patched build starting to show them too.

They are registered rather than written, so they seed only the fallback layer: a value already
stored for either key still wins, which keeps the overlays reachable for testing by clearing or
setting the preference directly.

### Background music suspension

**Files:** `Project/AudioManager.m` — `-init`, and the `-patchSuspendBgm:` and
`-patchSessionInterrupted:` handlers.

_Modern iOS._ The binary raises its `isBgmSuspended` flag only from `-audioPlayerBeginInterruption:`
(0x78da0) and the `AVAudioSession` delegate pair `-beginInterruption` / `-endInterruption` (0x78ebc,
0x78ed0). Those are `AVAudioPlayer` and `AVAudioSession` delegate callbacks that a current release
no longer delivers, so the flag can never be raised and `-appDidBecomeActive:` (0x78ee0) has nothing
to resume. The patch registers two further observers in `-init` — for
`UIApplicationDidEnterBackgroundNotification` and `AVAudioSessionInterruptionNotification` — and
drives the same flag from the notifications that replaced those callbacks. The resume path is left
untouched, and the player is paused rather than stopped so that `-appDidBecomeActive:`'s `-play`
continues from where it left off.

The two handlers and the two registrations are one change in two places: without the registrations
the handlers would be unreferenced, and without the handlers the registrations would name missing
selectors.

### Marker install detection

**File:** `Project/MarkerManager.m` — `+checkRegularMarkerData` (0x1b8fe0)

_Dead service._ The binary reconciles the persisted marker list against the marker directory in one
direction only: an entry whose archive fails `+checkMarkerData:` (0x1b7f00) has its version rewritten
to the `0.0.0` uninstalled sentinel, but an entry whose archive is present while its stored version
is still `0.0.0` is left alone. Entries were only ever promoted out of `0.0.0` on the download path.
The patch adds the opposite arm, so an archive that verifies is marked installed at `1.0.0`. Without
it a marker copied into the marker directory by hand stays flagged uninstalled,
`+getCurrentMarkerList` (0x1b7a04) filters it out, and the marker picker opens empty.

### Marker select availability

**File:** `Project/MarkerManager.m` — `+enableMarkerSelect` (0x1b94ec)

_Dead service._ The binary enables the marker button only once every reserved marker has been
downloaded: it scans for entries still at `0.0.0`, extracts the numeric part of each `mk%04d`
identifier, and returns `NO` if any is below `kReservedMarkerSize`. That condition can never be
satisfied again, so the button on the song-select screen is permanently disabled. The patch returns
`YES` as soon as any entry's archive passes `+checkMarkerData:`, preserving the apparent intent — do
not open a picker with nothing in it — without depending on the server. The faithful body is kept
under `#else`.

### Fallback to the bundled marker

**File:** `Project/MarkerManager.m` — `+moveMarkerDataInDoc` (0x1b96f4)

_Dead service._ The binary copies the bundled `mk0026` marker out of the application bundle and
returns, never touching `PrefCurrentMarkerID`; pointing that preference at the bundled marker was
the job of `+createDefaultMarkerList`, which only runs when no marker list exists at all. The
bundled `DefaultSettings.plist` ships a populated list and pre-seeds `PrefCurrentMarkerID` with
`mk0017`, so that never happens and the game builds its marker atlas from a download-only archive
that cannot exist — drawing no note markers at all while judgement and scoring continue. The patch
resets the preference to `mk0026` when the current marker's archive is missing or fails
verification.

### Music-select background fill

**File:** `Project/MusicSelectViewController.m` — `-loadView` (0x22e78)

_Modern iOS._ The still background is created with `-initWithImage:`, so it takes the artwork's
natural size, and the binary assigns a frame only in a few narrow phone cases. The bundled iPad
artwork is 768x1024, which filled the screen in 2011 but leaves 256 points bare down the right edge
and 342 along the bottom on a 1024x1366 iPad. The patch sets the image view's frame to the view's
bounds with `UIViewContentModeScaleAspectFill` and clipping. Aspect fill rather than scale-to-fill
so a future size cannot distort the artwork; the two aspect ratios are close enough that
essentially nothing is cropped.

### Store-promotion balloon

**File:** `Project/MusicSelectViewController.m` — `-loadView` (0x22e78)

_Dead service._ When the player owns no purchased music but has played the built-in songs, the
binary builds a balloon beside the store button advertising the store. It is compiled out for two
reasons: the store no longer answers, and the balloon's text is broken in the original. Its
localised key is `StoreBalloonMessage(%@)`, passed straight to `-initWithFormat:` with no variadic
argument, so the format's `%@` is left dangling and renders whatever occupies that slot.

The balloon's seven file-scope constants are wrapped in the same `#ifndef`, since nothing else uses
them and an unused constant fails the build under `-Werror`.

### Settings sheet presentation guard

**File:** `Project/MusicSelectViewController.m` — `-tapSettings:` (0x2d030)

_Modern iOS._ The binary presents the settings sheet and then latches its modal state
unconditionally — `bOpenModal` at 0x2d120, `bOpenSetting` at 0x2d12c, then `-musicShuffleDisable`
and `-setSearchEnable:NO` — without ever examining the result. In 2012 `-presentViewController:`
always succeeded; modern UIKit ignores it while a sheet is already presented or is still dismissing.
Because `-settingsNavViewClose:` (0x2d20c) holds the only clear of `bOpenSetting` in the whole
binary, and is reachable only from the sheet's own Close button, a swallowed presentation leaves the
song-select screen with its shuffle disabled and every swipe recogniser off, and no sheet on screen
to recover from.

The patch returns early when something is already presented, and otherwise sends `-settingClose`
first. That is the binary's own recovery primitive for the single reused controller: `-popoverClose`
(0x33930) and `-resumeJcfDownload` (0x33c40) both call it before tearing the sheet down, and it
closes any alert and pops back to the root child.

### Settings navigation-bar touch exclusivity

**Files:** `Project/SettingsViewController.m` — `-viewDidLoad` (0xe7268);
`Project/TermsViewController.m` — `-viewDidLoad` (0x113be0).

_Modern iOS._ Both methods mark the shared navigation bar `exclusiveTouch` and loop over
`navigationBar.subviews` marking each of those too. The idiom dates from when a navigation bar's
direct subviews were its per-item button views, so it meant no two bar buttons could track a touch
at once. Modern UIKit gives the bar full-width private containers instead, and the first call marks
the bar itself, so the whole bar becomes an exclusive-touch region of the window it shares with the
presenting screen. Both are compiled out.

### Settings cell accessory view

**File:** `Project/SettingsViewController.m` — `-tableView:cellForRowAtIndexPath:` (0xe5678)

_Modern iOS._ The binary sets an accessory view on exactly one row, Show Combos, and the view it
sets is the single `switchCombo` built in `-loadView`. No arm ever clears it, and the reuse
identifier is keyed on the cell style rather than the row, so Show Combos shares a reuse pool with
about ten other rows. Any recycling that hands the switch's cell to one of those rows while Show
Combos is rebuilt leaves two cells holding one accessory view.

On the SDK this shipped against a cell laid its accessory view out where it found it. Modern UIKit
re-parents it, so each of the two cells invalidates the other's layout in turn and the layout pass
never converges: the main thread spins inside the Core Animation commit and never returns to the
run loop, which locks the whole app. The patch clears a stale `accessoryView` on every row that is
not Show Combos.

### Settings sheet interactive dismissal

**Files:** `Project/SettingsNavController.m` — `-init` (0xe43ac), `-viewWillAppear:` (0xe4a20), and
a `-presentationControllerWillDismiss:` that is not in the binary at all.

_Modern iOS._ The sheet's `modalPresentationStyle` is `UIModalPresentationFormSheet` (`mov w2,#0x2`
at 0xe4408), which was not interactively dismissible when the game shipped, so the binary can assume
the Close item is the only way out. Since iOS 13 a sheet can be dismissed by a swipe or by a tap
outside it, and neither reaches `-pushClose:` (0xe4844), so neither reaches the only code path that
clears the song-select screen's modal state.

Refusing the dismissal would keep that state consistent, but it would also take away a way out of
the screen that the shipped binary running on the same system has. The binary shows the shape of
the better answer elsewhere: it implements `-popoverPresentationControllerDidDismissPopover:`
(0x27634) precisely to clean up after a dismissal the system initiated. This is that, for a sheet.
The controller makes itself its own `UIAdaptivePresentationControllerDelegate` and, when UIKit
reports the dismissal, calls the same `-pushClose:` the Close button calls, so `bOpenSetting` is
cleared and the select screen's shuffle and swipe recognisers come back exactly as they do on the
Close path. The two paths cannot double up, because UIKit sends this only for a user-initiated
dismissal and never for a programmatic one.

The `will` form is used rather than the `did` form because `-settingsNavViewClose:` plays the close
sound as its first act, and the Close button reaches it on touch-up. The `did` form runs only once
the dismissal has finished, which delays that sound by the whole animation and makes the same
action sound different depending on how it was invoked.

The delegate is assigned in both `-init` and `-viewWillAppear:`. `-init` reaches the presentation
controller before there is a presentation, where UIKit is entitled to return nil and the assignment
would be a silent no-op; the second assignment is the one that is guaranteed to take.

### Timing-adjust display link

**File:** `Project/SettingsTimingAdjustViewController.m` — `-viewWillDisappear:` (0x175528)

_Modern iOS._ `-startAnimation` runs from `-init` and nothing ever takes the link down again:
`-stopAnimation` (0x1762a8) is dead code in the shipped binary, and neither `-viewWillDisappear:`,
`-viewDidDisappear:` (0x1755b8) nor `-dealloc` (0x17596c) touches it. Because `CADisplayLink`
retains its target, the controller outlives the pop and keeps firing `-loop:` at 30 Hz forever,
driving `-[AdjustTestView draw]` and its `-presentRenderbuffer:` into a `CAEAGLLayer` that UIKit is
concurrently animating and re-parenting. The patch takes the link down before the transition starts.

### Store navigation bar appearance

**Files:** `Project/RotatableNavigationController.{h,m}` — `-patchApplyOpaqueBarAppearance`;
`Project/StoreViewController.m` and `Project/StoreViewControllerV2.m` — `-init`.

_Modern iOS._ `-[StoreViewController init]` (0x89460) says nothing to its four navigation bars but
`-setTranslucent:NO` (0x8956c, 0x89600, 0x89690, 0x89724). It sets no bar style, no bar tint and no
background image, and the binary contains no `UIAppearance` proxy at all, so the store deliberately
took UIKit's stock opaque bar. iOS 15 made every navigation bar consult `scrollEdgeAppearance` and
derive a transparent background when it is nil, while the legacy `translucent` flag feeds only
`standardAppearance`. The bar therefore paints nothing and the black window shows through. The patch
restates "stock opaque bar" in the modern spelling and pins no colour, since the patched build
already forces the light appearance.

It is an opt-in method rather than a `-viewDidLoad` override on `RotatableNavigationController`,
because `SettingsNavController` and `JcfManageNavController` derive from that class and style their
own bars, and the song-select screen builds its playlist bar from it directly. Only the store's
bars call it.

### Store cover over the tab bar

**File:** `Project/StoreViewController.m` — `-loadInitialStoreInfo` (0x899ec)

_Dead service._ The `usrPolicyView` cover runs from the navigation bar to the bottom of the screen,
so it lies over the tab bar as well, and the server-error label is added to it. With the store's
servers gone that error path is the normal one, so the cover comes up, dims the whole store and
takes every touch, and the tabs can no longer be tapped. The patch stops the cover short of the tab
bar so the tabs stay reachable.

### Store dead-service cover

**File:** `Project/StoreViewController.m` — `-dispErrorLabel:` (0x8ec24),
`-agreementError:msgStr:` (0x8ff68), and the else arm of `-downloaderError:` (0x8f8b8).

_Dead service._ `-becomeCoverView` (0x8e9bc) raises the same cover to full opacity, and
`-resignCoverView` is the only thing that lowers it. That method has exactly two call sites in the
binary, 0x8f4c8 and 0x8f830, both inside `-downloaderFinished:` (0x8f170) on a success reply from a
server that no longer answers. Every launch therefore takes the error branch, the cover goes up, and
nothing lowers it. The Manage tab is the visible victim because it needs no network at all. The
three error paths leave the cover down instead.

Three things this patch deliberately does not do:

- It does not set `userInteractionEnabled`. `usrPolicyView` owns the `LicenseAgreementView` board as
  a subview, so hit-testing would return nil for that whole subtree and nothing restores it. Setting
  the alpha is enough, because UIKit already skips hit-testing below an alpha of 0.01.
- It does not remove or nil the cover. `-agreementError:msgStr:` is invoked from
  `-[LicenseAgreementView sendErrorDelegate:]` (0x1f5928) with the board's own frame still on the
  stack, and the cover is that board's only strong owner.
- It does not drive the store forward, which would enter a state the binary never enters.

`-becomePolicyAgreement:` is untouched: it is the shared choke point, and `LicenseAgreementView`
reaches it on the branch that builds a genuine agreement board. The error label's three file-scope
constants are guarded alongside, since the patched build never constructs the label.

The user loses the on-screen "Unable to connect to server." message on these paths; the label is not
built rather than hidden.

## Bundle metadata

### Light appearance

**Files:** `CMakeLists.txt` (the `APP_USER_INTERFACE_STYLE_ENTRY` block), `Info.plist.in`.

_Modern iOS._ The app predates iOS 13, so every colour it picks assumes the light appearance, and
under the dark appearance the system-drawn surfaces invert while the artwork does not.
`UIUserInterfaceStyle` is app-wide, so it covers every window rather than only the one the app
delegate builds. CMake substitutes the key into `Info.plist.in` when `ENABLE_PATCHES` is on and an
empty string otherwise, so a faithful build keeps the original plist exactly.

Because this is a configure-time substitution rather than a compile-time one, toggling the flag
requires re-running CMake to regenerate `Info.plist`.
